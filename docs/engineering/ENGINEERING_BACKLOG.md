## ⚠️ Known safety-relevant limitation found (14 July 2026, live test with Ann)

**Finding:** With only Christian enrolled, Christian pointed the camera at Ann. The matcher returned `christian` as the identified profile instead of "Person Unknown." Confirmed with Christian: Ann's face had never been enrolled — the matcher had only Christian's 5 stored samples to compare against.

**Root cause (methodological, not a wiring bug):** `FaceSignatureEngine`'s 8-value geometry-ratio signature (relative spacing of eyes/nose/mouth/jaw, normalised by inter-ocular distance) is not discriminative enough to reliably separate two different real faces — this was flagged from the start as "Foundation-grade, not biometric-grade" (see the v0.16 scoping doc and manifest), but this is the first live evidence of *how* that weakness actually fails: an unenrolled person's ratios can land within `DEFAULT_DISTANCE_SCALE` (0.6) of an enrolled person's samples often enough to cross both `MIN_CANDIDATE_CONFIDENCE` (0.5) and — more seriously — the `IDENTITY_ACTIVE_PERSON_CONFIDENCE_THRESHOLD` (0.85) that gates `setActivePerson()`. There is no "closed-set" protection: the matcher always returns whichever enrolled person is *closest*, with no check for how *confidently* closest, or how the field would separate if more people were enrolled.

**Why this matters more than an ordinary bug:** this system exists partly to protect Finley (a protected user) and route the right personal context to the right person. Misidentifying a different real household member as Christian — especially if it could go the other way (misidentifying Finley or an unknown visitor as a trusted/owner profile) — is a real safety-relevant failure mode, not just an accuracy nitpick.

**Not yet done:** re-testing with Ann actually enrolled, to see whether the matcher can discriminate two *enrolled* real people, or whether it fails even then (this would tell us whether tightening the confidence thresholds is a viable mitigation, or whether the geometry-ratio approach needs to be replaced with a real face-embedding model sooner rather than later — Option B from the original scoping doc, already designed as a drop-in replacement behind `FaceRecognitionService`'s existing interface).

**Recommendation:** do not treat v0.16 as validated for anything beyond single-known-person demo purposes until this is re-tested with 2+ enrolled people. Until then, `shouldActivatePerson()`'s 0.85 gate should be treated as "reduces the risk," not "prevents misidentification."

**RESOLVED 14 July 2026 — matcher replaced, not just tuned.** Christian's call: "this is not good enough at this stage." Rather than retuning thresholds on a matcher that fundamentally isn't discriminative, swapped the whole matcher — this is the "Option B" upgrade the v0.16 scoping doc explicitly designed `FaceRecognitionService`'s interface to allow as a drop-in replacement.

- **New: `services/vision/FaceEmbeddingService.js`** — real on-device face-embedding provider via `@vladmandic/face-api` (TensorFlow.js-based, pinned to `1.7.15`, models loaded from `https://cdn.jsdelivr.net/npm/@vladmandic/face-api@1.7.15/model`, same CDN-pinning discipline as the MediaPipe models). Produces a 128-d descriptor per face using `tinyFaceDetector` + `faceLandmark68Net` + `faceRecognitionNet` — a real model trained (triplet loss) specifically to separate different people's faces, not just measure proportions. Same graceful-degrade contract as `PoseDetectionService`/`FaceLandmarkService`.
- **New: `services/identity/FaceEmbeddingEngine.js`** — pure comparison math (Euclidean distance + distance-to-confidence curve, scale 0.6 — the standard accept threshold for this class of descriptor model), mirroring `FaceSignatureEngine`'s shape so `FaceRecognitionService` barely changed. Fully unit-testable with synthetic descriptor arrays; the real model inference is not exercised in tests (same convention as MediaPipe).
- **`FaceRecognitionService.js` rewritten** to compare embeddings instead of geometry ratios. `recognise()`/`enroll()` now take `embedding` instead of `landmarks`. Provider renamed `FACE_RECOGNITION_LANDMARK_GEOMETRY` → `FACE_RECOGNITION_EMBEDDING_NET` (now exported as `RECOGNITION_PROVIDER`, imported by `IdentityEngine` instead of duplicating the string). `MIN_CANDIDATE_CONFIDENCE` (0.5) and `IDENTITY_ACTIVE_PERSON_CONFIDENCE_THRESHOLD` (0.85, unchanged, in `IdentityTypes.js`) kept as-is deliberately — the goal was fixing the matcher's discriminative power, not compensating for a weak matcher with stricter gates.
- **`VisionPipeline.js`** now also computes `faceEmbedding` (via `FaceEmbeddingService`, from the raw frame — the embedding model runs its own detection/alignment, doesn't reuse MediaPipe's landmarks) alongside the existing `faceLandmarks` (kept — still used for `FaceQualityEngine` gating and `FaceFoundationEngine`, untouched).
- **`FaceSignatureEngine.js` kept, not deleted** — marked superseded in its header, still real and still unit tested, available as a future secondary geometry check if ever wanted.
- **Smoke tests rewritten** (`FaceRecognitionFoundationSmokeTest.test.js`): synthetic 128-d descriptor fixtures replace the landmark fixtures, plus a new explicit test — `'does not confuse a second enrolled person with the first (the exact scenario found live with Ann)'` — enrolling two different synthetic people and confirming each resolves to their own profile, directly covering the failure mode Christian found live.
- **`package.json`** — added `@vladmandic/face-api@^1.7.15`. Installed successfully by Christian 14 July 2026.
- **`vite.config.js` — added a resolve alias for `@vladmandic/face-api`, found via `npm run release-check` failing (14 July 2026).** The package's `"main"` field points at its NodeJS build (`dist/face-api.node.js`), which itself requires `@tensorflow/tfjs-node` — a native binding MARS never wants (browser-only usage). Vite's own dev/build already prefers the `"browser"`/`"module"` field and resolves correctly, but Vitest runs tests under Node and follows `"main"`, so 3 test suites that transitively import `VisionPipeline.js` (`DiagnosticsStabilisationSmokeTest`, `LivePipelineWiringSmokeTest`, `VisionPipelineSmokeTest`) failed with `Cannot find module '@tensorflow/tfjs-node'`. All 205 previously-passing tests were unaffected (still green) — only the 3 suites that couldn't even load their module graph failed, and none of them exercise face-embedding logic directly (they failed at import-time, not from any assertion).

- **RESOLVED — live UI test with the real embedding matcher (14 July 2026).** Camera started clean, no TensorFlow/face-api console errors, real 128-d descriptors flowing every frame. Enrolled Christian live: match confidence held steady ~0.68–0.72 across repeated frames (real embedding distance ≈0.18–0.2) — clearly above the 0.5 recognition floor, correctly identified every time, but consistently below the 0.85 activation threshold this session (didn't confirm whether `setActivePerson` fired fresh vs. carried over from a prior session's persisted active-person value — `MemoryIntelligenceService` persists across reloads, `FaceEnrollmentStore` at the time did not, so this was ambiguous). Flagged as an open tuning question: `DEFAULT_DISTANCE_SCALE` (0.6) may be conservative for this household's actual camera/lighting — real two-person data (below) will clarify whether it needs adjusting.

## Resolved (16 July 2026, v0.16.4 Multi-Person Simultaneous Recognition & Live Video Overlay)

Built at Christian's request immediately after gap #2 above was identified, plus a live video overlay he asked for in the same conversation.

- **`FaceEmbeddingService.js` — new `detectFaces(frame)`.** Switched from `faceapi.detectSingleFace(...)` to `faceapi.detectAllFaces(...).withFaceLandmarks().withFaceDescriptors()`. Returns every detected face as `{ descriptor, box, landmarks, confidence }`, sorted largest-box-first. `computeEmbedding()` (the old single-face method) is left in place, unused by `VisionPipeline` now but kept for any caller that only ever wanted the primary face. Same graceful-degrade contract (no frame/model/face never throws) and same dynamic-import-inside-`initialise()` pattern as before, so the existing Vitest module-resolution/TensorFlow-side-effect fixes from the v0.16.1 matcher swap still apply untouched.
- **`VisionPipeline.js`** — now calls `detectFaces()` once per frame. `faceEmbedding` (singular) is set to `faces[0]?.descriptor` — the largest/most-prominent face — so every existing single-primary-person consumer (`IdentityTrackingService`, `IdentityEngine`, `MemoryIntelligenceService.setActivePerson()`, `IdentityStatusCard`, Vision Diagnostics) keeps working exactly as before, with zero behaviour change. Two new fields added to `perceptionResult`/`finalResult`/`errorResult()`: `faces` (the full raw array from `detectFaces()`) and `facesRoster` (see next item).
- **New: `services/identity/FaceRosterService.js`.** Builds a lightweight per-frame roster — `{ box, matched, profileId, displayName, confidence }` per detected face — purely for display. Deliberately separate from `IdentityEngine`: reuses `FaceRecognitionService.matchBest()` (already public) directly rather than going through the quality-gated, state-machine-backed `recognise()`/`evaluate()` path, so the safety-critical trust/pending-profile/memory-activation machinery is completely untouched and keeps deciding "who does MARS trust" based solely on the single primary face, same as v0.16.1. This roster only answers "who's visibly on screen right now."
- **New: `services/vision/FaceCaptureUiStore.js`.** Tiny singleton (same pattern as `LivePipelineStore`) so `useFaceEnrollment.js` (Identity tab) can signal `VisionFaceOverlay` (Vision tab, always-mounted camera per v0.16.1's tab-independent camera lifecycle) that an enrollment capture is in progress, without prop-drilling across unrelated tabs.
- **New: `components/mars/VisionFaceOverlay.jsx`.** Absolutely-positioned SVG sibling of the live `<video>` element in `VisionPanel.jsx`. Draws a bounding box + name label (green if matched, amber "Unknown" if not) per person in `facesRoster`, and — only while `FaceCaptureUiStore.isCapturing()` is true — the primary face's raw landmark points as a dot overlay, so there's a visible cue a face is actually being scanned during enrollment. Uses `viewBox="0 0 videoWidth videoHeight"` with `preserveAspectRatio="xMidYMid slice"` so face-api's native-pixel box/landmark coordinates line up with the video's own `object-cover` crop with no manual scale/offset math.
- **Smoke tests added** to `FaceRecognitionFoundationSmokeTest.test.js`: `FaceRosterService` correctly identifies two different enrolled people (Christian + Ann) in the *same* frame simultaneously and leaves a third, unenrolled "stranger" descriptor labeled Unknown; `FaceEmbeddingService.detectFaces()` gracefully degrades to an empty `faces` array with no frame/dataUrl (never touches real face-api under Vitest, same convention as every other face-api test). `VisionPipelineSmokeTest.test.js` and `LivePipelineWiringSmokeTest.test.js` extended to assert the new `faces`/`facesRoster` fields exist (empty, since these tests never exercise real model inference) on both the success and error paths.
- **Not yet built:** no face-selection UI — if multiple people are in frame during enrollment, `useFaceEnrollment.js` still always captures whichever face `detectFaces()` ranks largest/primary, with no way to pick a specific detected face to enroll if that's not the one you want. No continuous per-person tracking across frames for the roster (it's a fresh independent classification every frame, not a tracked identity per person) — fine for "who's visible right now" display, but not a foundation for e.g. per-visitor visit history. `npm run release-check` and a live multi-person UI test (two people in frame at once) are still pending — Christian's call on when to run those.

## Resolved (16 July 2026, v0.16.5 Guided Multi-Pose Enrollment)

Built immediately after v0.16.4, closing the other gap from the same live test (16 July 2026, Christian): "still only capturing [near-identical] images."

- **`hooks/useFaceEnrollment.js` — replaced the blind capture loop.** Was: 4 samples, 600ms apart, ~2.4s total, while the person sits still facing the camera up close (near-duplicate frames, sensor noise only). Now: a `POSE_STEPS` sequence of 5 named steps — look straight, turn head slightly left, turn slightly right, tilt chin down, step back — each with a `holdMs` pause and an instruction string exposed as `currentStepLabel`. `matchBest()` (`FaceRecognitionService.js`) already does nearest-neighbor matching across every stored sample per person rather than an average, so it directly benefits from this — enrollment just wasn't feeding it diverse samples before.
- **`FaceEnrollmentStore.js` — `MAX_SAMPLES_PER_PERSON` raised 5 → 10.** Comfortably holds one full 5-step guided pass, with room for a second enroll/re-enroll pass to blend in rather than immediately evicting the first pass's samples. Existing "caps stored samples and drops the oldest" test updated (12 enrolls → cap of 10, was 7 enrolls → cap of 5) to match.
- **`components/identity/FaceEnrollmentPanel.jsx`** — shows `currentStepLabel` as a live instruction banner during capture (e.g. "Tilt your chin down a little") instead of a bare "Capturing X/Y..." counter with no guidance on what to actually do.
- **Not yet built:** no test coverage for the guided sequence itself (the hook's 5×1.3s of real timers make it a poor fit for Vitest's existing convention of testing pure services/engines, not React hooks with async timing — verified live instead, same as `useIdentityFoundation`/`useFaceEnrollment` always have been). No per-step "retry this pose" control if one step visibly failed (e.g. face left frame mid-hold) — a failed step is silently recorded as `skipped_no_embedding` and the sequence continues. `npm run release-check` and a live guided-enrollment UI test are still pending.

## Resolved (16 July 2026, v0.16.6 Enrollment Camera Preview & Quality-Gated Capture)

A single `MediaStream` can feed more than one `<video>` element's `srcObject` at once, so this just hands out the same stream reference to whichever component asks — no second camera acquisition, no permission re-prompt. `VisionPanel.jsx`'s `startCamera()`/`stopCamera()` now call `setStream()`/`clearStream()`.

- **`hooks/useFaceEnrollment.js` — replaced the fixed per-step sleep with `waitForUsableFrame()`.** Was: wait `holdMs` (1300ms), then grab whatever `faceEmbedding` happens to be in `LivePipelineStore` at that instant, even if it's stale or momentarily empty (person blinked, turned too far, etc.). New `stepStatus` (`'waiting' | 'captured' | 'timeout'`) lets both `FaceEnrollmentPanel.jsx` and the new pop-up show a "Captured!" confirmation before the sequence advances to the next pose — the "only go to the next frame once it's confirmed" behaviour Christian asked for.

- **Not yet built:** no visible countdown/progress bar for the up-to-6s wait within a single step (just the instruction text and, implicitly, however long it takes). If a step times out, there's no dedicated retry button for just that pose — the sequence still moves on and the person can only re-run the whole `Re-enroll` flow. `npm run release-check` is still pending.

## Resolved (16 July 2026, v0.16.7 Voice-Narrated Enrollment)

Even with v0.16.6's pop-up preview and step confirmation, Christian's next live test found it "still WAY to quick and it dint pause until the next required pose is ok" — and asked for the app to speak each pose out loud.

- **New: `services/voice/SpeechOutputService.js`.** A small reusable text-to-speech wrapper around the browser's Web Speech API, extracted from the `speak()` function that previously lived only inline in `ChatPanel.jsx` (same voice settings: `en-GB`, rate 0.95, pitch 0.9, so it's recognisably the same "voice" everywhere). `speak(text)` returns a promise that resolves once speech actually finishes — or, if speech synthesis isn't supported, or the browser never fires the utterance's `end` event (headless environments, missing voices, etc.), after a generous length-based fallback timeout (1.5–8s, scaled by text length) so nothing can await it forever.
- **`hooks/useFaceEnrollment.js` — replaced the fixed `POST_SPEECH_SETTLE_MS`/timer-only pacing with real narration.** Speaks an intro line ("Let's get a quick scan of your face. Hold each pose when I ask.") before the sequence starts, then speaks each pose's instruction text and *actually waits for it to finish* before starting `waitForUsableFrame()` (still followed by a short 500ms settle beat, since even after hearing an instruction a person needs a moment to physically move). This makes real speech duration the pacing mechanism — a short instruction ("Look straight at the camera") naturally takes less time than a long one ("Slowly turn your head slightly to the left"), the same way it would if a person were giving the instructions, rather than a single guessed constant that was either too short for long instructions or unnecessarily long for short ones. A short spoken wrap-up line ("Got it, thanks!" / "I couldn't get a clear picture. Let's try that again.") plays after the sequence finishes, fired without blocking the result being recorded.
- **Live-tested** (enrolling Finley via the real UI): sequence audibly paced by speech, pop-up preview and step confirmations still worked exactly as v0.16.6 left them, 5/5 samples captured, no console errors beyond the pre-existing benign MediaPipe info line. Test enrollment cleared afterward (same known face-selection limitation as before — a single-camera capture always attributes to whichever profile was clicked).
- **Not yet built:** no user-facing mute/volume control for the enrollment narration specifically (it uses whatever the browser's default speech output routing is). No spoken retry prompt if a step times out — the visual "Couldn't get a clear frame" message has no spoken counterpart yet. `npm run release-check` is still pending.

## Resolved (16 July 2026, v0.16.8 Add New People)

Christian asked "how can we add more users" — the three seeded profiles (Christian/Ann/Finley) were hardcoded in `PersonRegistry.js` with no path to add anyone else, and enrollment (v0.16.1+) could only ever enroll a face against one of those three.

- **`services/identity/PersonRegistry.js` — new `addProfile({ displayName, userType })` and `removeProfile(profileId)`.** `addProfile` generates a unique id by slugifying the display name (appending `-2`, `-3`, etc. on a collision), only accepts `TRUSTED_USER` / `PROTECTED_USER` / `GUEST` as the requested `userType` (falls back to `TRUSTED_USER` for anything else, including a spoofed `OWNER` — owner profiles still can't be created through any UI path, same rule `ProfileAuthorisationService` already enforced for the auto-detected pending-profile flow). `removeProfile` only ever removes a profile tracked in a new internal `customProfileIds` set — the three `DEFAULT_PROFILES` are never added to that set, so they can never be removed this way.

## Resolved (17 July 2026, v0.16.11 Identity Lock)

Christian: "once its id'd someone at a high percentage can it lock in and track. if yes look up what percentage is a good lock on." Then, once scoped: "yes build. it will be very importent as for example if finley has a sezure and is on the floor face id will not recognize him a a seizue could be missed but if it has a lock on it will continue to recognise the person on the floor without face it."

- **`services/identity/IdentityLockService.js` — new.** Pure per-`trackingId` lock state machine (`none` → `locking` → `locked`). Once a face match sustains `IDENTITY_LOCK_ACQUIRE_CONFIDENCE_THRESHOLD` (0.9) for `IDENTITY_LOCK_ACQUIRE_CONSECUTIVE_FRAMES` (3) consecutive frames, the lock keeps reporting that person through frames with no qualifying face evidence, as long as the underlying track stays alive. Releases only when a *different* profile clears `IDENTITY_LOCK_OVERRIDE_CONFIDENCE_THRESHOLD` (0.75) on the same track, or the track itself expires. Consecutive-frame counter decrements by 1 (floored at 0) on a sub-threshold frame rather than hard-resetting — tolerates isolated noisy frames (a blink, motion blur) without discarding an otherwise-good streak.
- **Two pre-existing bugs found and fixed as prerequisites**, neither of which Christian asked about directly — both surfaced while building the lock:
  1. `VisionPipeline.js` never passed a `trackingId` into `IdentityEngine.evaluate()`, so `IdentityTrackingService` minted a brand-new track on literally every frame — no continuity ever existed in the live pipeline despite the architecture being designed for it. Fixed with `resolveTrackingId()`, which now reuses the single most-recently-seen active track.
  2. `IdentityStateMachine.evaluate()` had an unconditional `if (!faceDetected) return TRACKING`, discarding the matched profile the instant face detection failed — the exact failure mode the seizure scenario describes. Now only falls back to generic `TRACKING` when there's *also* no matched profile to fall back on.
- **Live-testing exposed a third, deeper, pre-existing bug in the confidence scale itself.** Three straight lock-acquire threshold attempts (0.9 → 0.8 → 0.75) all failed to acquire live. Christian caught the real clue by noticing the UI showed two different, inconsistent "confidence" numbers in two different places ("is it worth noting there are two comfidence levels in two seperate aeras" / "not alwas 85") — investigation found *neither* was live face-match confidence: the Identity card's number is `IDENTITY_CONFIDENCE.TRUSTED` (a fixed per-state constant, 85), and the Vision Diagnostics "Person" card's number is a general pose/risk score. Reading the real value directly out of the running pipeline (console-instrumented `LivePipelineStore`) found the actual live `identityConfidence` for a genuinely good match (Christian's own face, Euclidean distance ≈0.27, well inside the 0.6 accept boundary) was only ~0.52–0.57 — barely above the 0.5 "is this even a candidate" floor. **Root cause:** `FaceEmbeddingEngine.distanceToConfidence()` used a linear formula (`1 - distance/scale`) that only awards 90%+ confidence to near-identical descriptors, which ordinary live pose/lighting variation never produces — no lock threshold tried could ever have worked, since the real ceiling for a good match sat below all three attempts. Given the choice between recalibrating the formula or just lowering the lock's thresholds further to work around it, Christian chose to fix the source ("Recalibrate the confidence scale (Recommended)"). Replaced with a logistic curve centred on the same 0.6 distance boundary (confidence exactly 0.5 at the boundary, rising toward 1 below it, falling toward 0 above it) — Christian's real 0.27-distance match now reads ~90–91%, not ~55%. `IDENTITY_LOCK_ACQUIRE_CONFIDENCE_THRESHOLD` restored to a genuine 0.9 "high percentage" bar once the scale was actually fixed, rather than left artificially low.
- **`services/identity/RecognitionCandidate.js`/`IdentityEngine.js`/`components/identity/IdentityStatusCard.jsx`** — new `identityHeld` flag threaded end to end: `RecognitionCandidate.deriveState()` treats a held lock the same as a live-recognised face; `IdentityStateMachine` appends "Tracking held through a face-visibility gap..." to the reason string; the Identity card shows a distinct amber "Tracking held" badge (deliberately visible, not silent — MARS is still making a safety-relevant claim about who this is, and that claim should read as held, not indistinguishable from a normal live-confirmed match).
- **Live-verified post-fix two ways.** (1) Confidence-scale fix confirmed directly against the real running pipeline: Christian's live face-match confidence now reads ~90–91%, up from the ~55% found before the fix. (2) The actual hold behaviour was verified by driving the app's own running `IdentityEngine`/`IdentityTrackingService`/`FaceEnrollmentStore` instances directly (via console) with Christian's real enrolled embedding, rather than a live webcam turn-away: three staged live attempts at physically turning away/occluding the camera on request didn't reliably produce a clean "person present, face genuinely undetectable" frame — the pose and face detectors have their own real-world limits (a full lens occlusion reads as no person at all; a side-profile turn is often still read as a detectable face) independent of the Identity Lock logic. Driving the real modules directly with a controlled synthetic no-face frame confirmed the actual code path: 3 confident frames → `state: trusted`, `identityHeld: false`; a following no-face-but-person-present frame → `state` stays `trusted` (not dropped to generic tracking), `identityHeld: true`, reason correctly appends "Tracking held through a face-visibility gap." This is the literal seizure/floor scenario Christian described, confirmed against the deployed code, not just the test suite.
- **21 new/updated smoke tests**: `IdentityLockService` unit tests (acquire timing, weak-match rejection, hold-through-no-candidate, override on rival match, ignore weak rival, immediate release), end-to-end pipeline tests (trackingId continuity, a seeded `finley` PROTECTED-state-survives-no-face test matching the exact motivating scenario, a negative control confirming a bare no-face frame *without* a prior lock still correctly shows generic tracking, and a track-expiry test), plus fixes to existing exact-value assertions (`toBe(0)`/`toBe(1)`) that broke because the new logistic curve is asymptotic rather than exact.
- **Known limitation, not new to this milestone:** track continuity is a "single active track" heuristic, not spatial/bounding-box re-identification. If a tracked person leaves and a different, unenrolled person takes their place within the same track-expiry window without a confident rival face match, the lock could theoretically keep reporting the old identity briefly. Consistent with MARS's existing single-primary-person architecture; flagged as an accepted trade-off, not a regression.
- **Not yet built:** no smoke-test coverage for `CameraStreamStore.requestStart()`/`setStartHandler()` (carried over from v0.16.9, still not urgent). `npm run release-check` still pending — hand off to Christian.

## Resolved (17 July 2026, v0.16.13 Multi-Person Simultaneous Locking)

Live-testing v0.16.12: "ok that worked with me then i got ann in to the picture detected ok both. locked on to her but then the lock turned off on me. looked like it could only lock on to one persone at a time." Then, once scoped: "it needs to tack more than one person especialy in development. in my case Finley is the priorary however there might be some places that need to to track and monitor more than one persone."

- **Root cause.** `IdentityTrackingService.resolveTrackingId()` (v0.16.11) only ever tracked ONE global slot — whichever track was most recently touched — and `VisionPipeline` only ever fed the single largest/most-prominent face into it (`faces[0]`). Whoever's face happened to be biggest/closest that frame owned the one shared trackingId, and therefore the one shared lock (`IdentityLockService` is keyed by trackingId). A second, simultaneously-visible recognised person's confident match didn't get their own lock — it stole the first person's.
- **`services/identity/IdentityTrackingService.js` — new `profileTrackMap` (profileId → trackingId).** `updateFromPerception()` reordered so face recognition runs BEFORE trackingId resolution — `resolveTrackingId(now, matchedProfileId, hasOwnFace)` now gives a confidently-matched profile its own dedicated, stable track, looked up (and remembered) independent of face size/position. An unmatched/pending face still falls back to the old single-slot heuristic (preserving SEARCHING-patience continuity for someone MARS doesn't know yet), but that fallback now excludes any track already claimed by a recognised profile — `hasOwnFace` distinguishes "a genuinely distinct unrecognised face this frame" (safe to exclude claimed tracks) from "no face at all this frame" (the whole-frame fallback the held-through-occlusion lock depends on, which MUST still be allowed to resume a claimed track). Claimed track slots are released when a track expires.
- **`services/vision/VisionPipeline.js` — runs the tracking/lock update for EVERY detected face, not just the largest.** A new per-face loop calls `IdentityTrackingService.updateFromPerception()` once per face (each with its own dedicated trackingId), then `IdentityEngine.evaluate()` reusing that same trackingResult (via the `trackingResult` option IdentityEngine already supported) — avoids a second, duplicate tracking call for the same face/frame, which would otherwise double-count `framesSeen` and corrupt the lock's consecutive-frame counter. Which ONE face drives the existing single decision/notification/memory-activation pipeline (unchanged below that point) is now chosen by priority — Christian: "Finley is the priority" — protected profile first, then anyone already locked, then the original largest-face default.
- **`components/mars/VisionFaceOverlay.jsx`** — replaced the single scalar `identityLocked` prop with a new `identityRoster` array (per-person lock status, from `VisionPipeline`), matched against each `facesRoster` entry by `profileId`. Every simultaneously-visible recognised+locked person now shows their own independent LOCKED badge, not just whoever is primary.
- **Live-verified against the real running app**, not just the test suite: drove `IdentityTrackingService.updateFromPerception()` directly with Christian's and Ann's actual enrolled embeddings, interleaved exactly like `VisionPipeline`'s per-face loop — confirmed distinct trackingIds, Christian's lock (`locked: true, personId: 'christian'`) stays intact after Ann joins and locks in alongside him (`locked: true, personId: 'ann'`), neither stealing the other's.
- **4 new smoke tests**: distinct trackingIds for two simultaneously-recognised people, the exact steal-prevention scenario (Christian locks, Ann joins and locks, Christian's lock still intact), an unrecognised bystander face cannot steal a recognised person's dedicated track, and a no-face whole-frame fallback still correctly resumes a claimed/locked track (proving held-through-occlusion continuity wasn't regressed).
- **Known, disclosed limitation — NOT solved by this milestone:** "held through a face-visibility gap" (v0.16.11) still only works reliably for whichever ONE person is primary that frame. The underlying person-presence signal (pose/body detection) is itself single-person, not multi-person — if a second, non-primary person's face drops out, MARS can't honestly tell that apart from them having genuinely left, since there's no independent presence signal for a specific second body. True simultaneous held-tracking for 2+ people (e.g. Finley on the floor while a caregiver is also in frame) needs multi-person body/pose presence detection — a materially bigger vision-pipeline change, logged here as a follow-up rather than silently claimed as solved.
- **Also not solved, pre-existing:** two simultaneously-*unrecognised* strangers in the same frame can still share a track within the same frame tick (the single-slot fallback resolves both against "the most recently touched unclaimed track," and the second call's resolution happens after the first has already touched it) — consistent with the already-disclosed "not spatial re-identification" limitation, not a new regression.
- **Not yet built:** no smoke-test coverage for the `VisionPipeline`-level priority-selection logic itself (protected > locked > largest) — `VisionPipeline`'s own tests can't exercise real multi-face detection in this environment (face-api needs actual image data), consistent with the existing convention of testing pipeline logic at the `IdentityTrackingService`/`IdentityLockService` layer instead. `npm run release-check` still pending — hand off to Christian.

## Roadmap addition: Multi-camera / distributed monitoring

Raised 13 July 2026 (Christian): extend MARS beyond the single S22-mounted camera to WiFi/Bluetooth pan-tilt cameras placed around the house, so monitoring isn't limited to whatever room the robot is physically in.

**Where this sits relative to current work:** this is a separate future phase, not part of v0.16. v0.16 (Face Recognition) and v0.17 (Protected User Alerting) both currently assume a single active camera source feeding one `VisionPipeline`. The right shape for a multi-camera system is: one MARS "brain" (identity/memory/decision/notification — all already person/session-scoped, not camera-scoped) consuming a stream of per-camera perception results, each tagged with a camera/location id, rather than one hardcoded camera. That's a moderate `CameraService`/`FrameCaptureService`/`VisionPipeline` refactor (they're currently singletons with no camera-id concept) plus a pairing/discovery UI for adding cameras, and is naturally easier to build once Identity (v0.16) already resolves a `personId` independent of which camera saw them — so a person recognized in the kitchen camera and later the hallway camera can resolve to the same active person.

**Recommendation:** treat this as its own roadmap phase, positioned after Face Recognition and Protected User Alerting are live (so multi-camera has a real identity/alerting system to plug into), not before. Added to the MVCH as **Phase 9 — Multi-Camera / Distributed Monitoring**, `v0.18.x`, sitting between Phase 8 (Protected User Alerting) and Robot Control — Christian's call, 13 July 2026, since it's a pure software/sensor extension that belongs before the hardware-control phases. Robot Control/Android/Mk1 Release were renumbered accordingly (now v0.19.x/v0.20.x/v0.21.x). Milestones: Camera Discovery & Pairing Foundation → Per-Camera Vision Pipeline (camera-id-tagged perception) → Cross-Camera Identity Continuity → Monitoring Dashboard (multi-feed). See `MVCH_Master_Version_Control_History.md`.

**What to do now, if anything:** nothing required for v0.16. The one thing worth keeping in mind while building Face Recognition: don't hardcode "the camera" in new code in a way that would require a rewrite later — e.g. if a new face-recognition service takes a frame, keep it agnostic to where that frame came from rather than reaching into `CameraService`'s singleton state directly. This is a design-awareness note, not new scope.
