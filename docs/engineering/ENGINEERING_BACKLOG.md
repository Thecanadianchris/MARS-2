## ⚠️ Known safety-relevant limitation found (14 July 2026, live test with Ann)

**Finding:** With only Christian enrolled, Christian pointed the camera at Ann. The matcher returned `christian` as the identified profile instead of "Person Unknown." Confirmed with Christian: Ann's face had never been enrolled — the matcher had only Christian's 5 stored samples to compare against.

**Root cause (methodological, not a wiring bug):** `FaceSignatureEngine`'s 8-value geometry-ratio signature (relative spacing of eyes/nose/mouth/jaw, normalised by inter-ocular distance) is not discriminative enough to reliably separate two different real faces — this was flagged from the start as "Foundation-grade, not biometric-grade" (see the v0.16 scoping doc and manifest), but this is the first live evidence of *how* that weakness actually fails: an unenrolled person's ratios can land within `DEFAULT_DISTANCE_SCALE` (0.6) of an enrolled person's samples often enough to cross both `MIN_CANDIDATE_CONFIDENCE` (0.5) and — more seriously — the `IDENTITY_ACTIVE_PERSON_CONFIDENCE_THRESHOLD` (0.85) that gates `setActivePerson()`. There is no "closed-set" protection: the matcher always returns whichever enrolled person is *closest*, with no check for how *confidently* closest, or how the field would separate if more people were enrolled.

**Why this matters more than an ordinary bug:** this system exists partly to protect Finley (a protected user) and route the right personal context to the right person. Misidentifying a different real household member as Christian — especially if it could go the other way (misidentifying Finley or an unknown visitor as a trusted/owner profile) — is a real safety-relevant failure mode, not just an accuracy nitpick.

**Not yet done:** re-testing with Ann actually enrolled, to see whether the matcher can discriminate two *enrolled* real people, or whether it fails even then (this would tell us whether tightening the confidence thresholds is a viable mitigation, or whether the geometry-ratio approach needs to be replaced with a real face-embedding model sooner rather than later — Option B from the original scoping doc, already designed as a drop-in replacement behind `FaceRecognitionService`'s existing interface).

**Recommendation:** do not treat v0.16 as validated for anything beyond single-known-person demo purposes until this is re-tested with 2+ enrolled people. Until then, `shouldActivatePerson()`'s 0.85 gate should be treated as "reduces the risk," not "prevents misidentification."

**RESOLVED 14 July 2026 — matcher replaced, not just tuned.** Christian's call: "this is not good enough at this stage." Rather than retuning thresholds on a matcher that fundamentally isn't discriminative, swapped the whole matcher — this is the "Option B" upgrade the v0.16 scoping doc explicitly designed `FaceRecognitionService`'s interface to allow as a drop-in replacement.

- **New: `services/vision/FaceEmbeddingService.js`** — real on-device face-embedding provider via `@vladmandic/face-api` (TensorFlow.js-based, pinned to `1.7.15`, models loaded from `https://cdn.jsdelivr.net/npm/@vladmandic/face-api@1.7.15/model`, same CDN-pinning discipline as the MediaPipe models). Produces a 128-d descriptor per face using `tinyFaceDetector` + `faceLandmark68Net` + `faceRecognitionNet` — a real model trained (triplet loss) specifically to separate different people's faces, not just measure proportions. Same graceful-degrade contract as `PoseDetectionService`/`FaceLandmarkService`.
- **New: `services/identity/FaceEmbeddingEngine.js`** — pure comparison math (Euclidean distance + distance-to-confidence curve, scale 0.6 — the standard accept threshold for this class of descriptor model), mirroring `FaceSignatureEngine`'s shape so `FaceRecognitionService` barely changed. Fully unit-testable with synthetic descriptor arrays; the real model inference is not exercised in tests (same convention as MediaPipe).
- **`FaceRecognitionService.js` rewritten** to compare embeddings instead of geometry ratios. `recognise()`/`enroll()` now take `embedding` instead of `landmarks`. Provider renamed `FACE_RECOGNITION_LANDMARK_GEOMETRY` → `FACE_RECOGNITION_EMBEDDING_NET` (now exported as `RECOGNITION_PROVIDER`, imported by `IdentityEngine` instead of duplicating the string). `MIN_CANDIDATE_CONFIDENCE` (0.5) and `IDENTITY_ACTIVE_PERSON_CONFIDENCE_THRESHOLD` (0.85, unchanged, in `IdentityTypes.js`) kept as-is deliberately — the goal was fixing the matcher's discriminative power, not compensating for a weak matcher with stricter gates.
- **`VisionPipeline.js`** now also computes `faceEmbedding` (via `FaceEmbeddingService`, from the raw frame — the embedding model runs its own detection/alignment, doesn't reuse MediaPipe's landmarks) alongside the existing `faceLandmarks` (kept — still used for `FaceQualityEngine` gating and `FaceFoundationEngine`, untouched).
- **`FaceSignatureEngine.js` kept, not deleted** — marked superseded in its header, still real and still unit tested, available as a future secondary geometry check if ever wanted.
- **Smoke tests rewritten** (`FaceRecognitionFoundationSmokeTest.test.js`): synthetic 128-d descriptor fixtures replace the landmark fixtures, plus a new explicit test — `'does not confuse a second enrolled person with the first (the exact scenario found live with Ann)'` — enrolling two different synthetic people and confirming each resolves to their own profile, directly covering the failure mode Christian found live.
- **`package.json`** — added `@vladmandic/face-api@^1.7.15`. Installed successfully by Christian 14 July 2026.
- **`vite.config.js` — added a resolve alias for `@vladmandic/face-api`, found via `npm run release-check` failing (14 July 2026).** The package's `"main"` field points at its NodeJS build (`dist/face-api.node.js`), which itself requires `@tensorflow/tfjs-node` — a native binding MARS never wants (browser-only usage). Vite's own dev/build already prefers the `"browser"`/`"module"` field and resolves correctly, but Vitest runs tests under Node and follows `"main"`, so 3 test suites that transitively import `VisionPipeline.js` (`DiagnosticsStabilisationSmokeTest`, `LivePipelineWiringSmokeTest`, `VisionPipelineSmokeTest`) failed with `Cannot find module '@tensorflow/tfjs-node'`. Fixed by aliasing `@vladmandic/face-api` directly to `./node_modules/@vladmandic/face-api/dist/face-api.esm.js` in `vite.config.js`'s `resolve.alias`, so both dev/build and Vitest resolve to the same browser ESM bundle. All 205 previously-passing tests were unaffected (still green) — only the 3 suites that couldn't even load their module graph failed, and none of them exercise face-embedding logic directly (they failed at import-time, not from any assertion).
- **Not yet done:** confirming `npm run release-check` passes clean after the alias fix (Christian re-running now), then the actual re-test with Ann enrolled for real (this was the whole point) — needs Christian, live camera, both of you. Also still open: whether `DEFAULT_DISTANCE_SCALE` (0.6) needs retuning once real two-person data exists — chosen from the literature's typical dlib/face-api accept threshold, not yet empirically validated against this household's actual faces/lighting/camera.

Don't grow v0.16's scope to answer this unless it turns out to matter for pending-profile confirmation permissions.
- **`CameraPreviewPanel.jsx` and `VisionPanel.jsx` appear to duplicate the same live-camera UI** (both independently manage camera lifecycle + render near-identical pipeline dumps). Confirm whether one is legacy before deleting either.

## Roadmap addition: Multi-camera / distributed monitoring

Raised 13 July 2026 (Christian): extend MARS beyond the single S22-mounted camera to WiFi/Bluetooth pan-tilt cameras placed around the house, so monitoring isn't limited to whatever room the robot is physically in.

**Where this sits relative to current work:** this is a separate future phase, not part of v0.16. v0.16 (Face Recognition) and v0.17 (Protected User Alerting) both currently assume a single active camera source feeding one `VisionPipeline`. The right shape for a multi-camera system is: one MARS "brain" (identity/memory/decision/notification — all already person/session-scoped, not camera-scoped) consuming a stream of per-camera perception results, each tagged with a camera/location id, rather than one hardcoded camera. That's a moderate `CameraService`/`FrameCaptureService`/`VisionPipeline` refactor (they're currently singletons with no camera-id concept) plus a pairing/discovery UI for adding cameras, and is naturally easier to build once Identity (v0.16) already resolves a `personId` independent of which camera saw them — so a person recognized in the kitchen camera and later the hallway camera can resolve to the same active person.

**Recommendation:** treat this as its own roadmap phase, positioned after Face Recognition and Protected User Alerting are live (so multi-camera has a real identity/alerting system to plug into), not before. Added to the MVCH as **Phase 9 — Multi-Camera / Distributed Monitoring**, `v0.18.x`, sitting between Phase 8 (Protected User Alerting) and Robot Control — Christian's call, 13 July 2026, since it's a pure software/sensor extension that belongs before the hardware-control phases. Robot Control/Android/Mk1 Release were renumbered accordingly (now v0.19.x/v0.20.x/v0.21.x). Milestones: Camera Discovery & Pairing Foundation → Per-Camera Vision Pipeline (camera-id-tagged perception) → Cross-Camera Identity Continuity → Monitoring Dashboard (multi-feed). See `MVCH_Master_Version_Control_History.md`.

**What to do now, if anything:** nothing required for v0.16. The one thing worth keeping in mind while building Face Recognition: don't hardcode "the camera" in new code in a way that would require a rewrite later — e.g. if a new face-recognition service takes a frame, keep it agnostic to where that frame came from rather than reaching into `CameraService`'s singleton state directly. This is a design-awareness note, not new scope.
