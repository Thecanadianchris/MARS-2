## 1. The decision: how should recognition actually work?

Three options, same as the kickoff brief flagged, now confirmed against real code rather than assumption:

**Option A — Landmark-geometry signature.** Use MediaPipe `FaceLandmarker` (already an available export of `@mediapipe/tasks-vision`, just unused — only `PoseDetectionService` is wired up today) to derive a distance/ratio signature per face, nearest-neighbour match against stored signatures. No new dependency, deterministic, testable. Weak to pose/lighting changes; not real biometric-grade matching.

**Option B — Real face-embedding model.** Add a proper embedding model (TFLite/ONNX or `face-api.js`). Real recognition quality. New dependency + model download, more surface area, heavier for a "Foundation" milestone, and bundle-size/offline implications need checking.

**Option C — Honest-stub Foundation.** Build the full pipeline end-to-end — a pluggable `FaceRecognitionService` interface that emits real `RecognitionCandidate`s with populated `identityConfidence` and `candidateProfiles`, wire it into `IdentityTrackingService`/`IdentityEngine.evaluateRecognitionCandidate`, build the registration flow on top of the existing `PersonRegistry` pending→confirm gate, and call `setActivePerson` on a confirmed match — but keep the actual matcher simple (could be Option A's geometry, or even a simulated/manual-entry matcher) behind that interface. Matches how every other Foundation this project (Voice, Identity, Behaviour) was built. Defers the hard ML problem to v0.16.1/v0.16.2 or the Android build.

**My recommendation, for Christian to accept or override: Option C.** The valuable and testable thing in a "Foundation" milestone is the wiring — a real interface producing real `RecognitionCandidate`s, a real registration flow, and the `setActivePerson` payoff actually firing — not whether the matcher is biometric-grade yet. `IdentityTrackingService` hardcoding `identityConfidence: 0` today means literally nothing can reach `KNOWN`/`TRUSTED` state yet regardless of which option is picked, so the wiring is the real unlock. Option A can be layered in as the initial matcher inside Option C's interface without changing the plan; Option B stays available as a drop-in replacement later.

**Question for Christian:** which option, and if C, do you want the initial matcher to be Option A's geometry approach, or something simpler still (e.g. simulated/manual identity confirmation only, like the current IdentityPanel scenario inputs) for v0.16 itself?

## 2. Safety rules to carry in (non-negotiable, confirmed consistent with existing code)

- Biometric data (any face signature/descriptor) stored on-device only, same posture as `PersonalContextService`'s on-prem-only rule for personal context. Never sent to the Cloud (Claude) tier or any network call.
- `setActivePerson` only fires on a confirmed match above a high confidence threshold — never a silent switch, and never onto a `protected: true` profile (`finley`) on a weak match, since that would misroute future alerting/context.
- Unknown faces are never auto-enrolled. They go through the existing `createPendingProfile` → `ProfileAuthorisationService.canConfirmProfile` → `confirmPendingProfile` gate, same as today.
- `medicalDiagnosis: false` carries forward unchanged. Face recognition answers "who," never anything clinical.
- Same regression discipline as Phase 6: additive wiring only, explicit guard tests, don't touch memory-writer paths or which turns escalate to the AI tiers.

## 3. Target flow (once Christian decides on §1)

```
camera frame (CameraService / FrameCaptureService)
  → FaceRecognitionService (NEW) produces a RecognitionCandidate
      - known match ≥ threshold → candidateProfiles: [{ profileId, confidence }]
      - unknown / low confidence → PENDING_PROFILE path (trusted-user confirm)
  → IdentityEngine.evaluateRecognitionCandidate(candidate)   [already exists, no changes needed]
  → resolves KNOWN / TRUSTED / PROTECTED / UNKNOWN / PENDING_PROFILE state
  → on a confirmed KNOWN/TRUSTED identity above threshold:
      MemoryIntelligenceService.setActivePerson(profile.id)   ← the payoff, already exists
  → next turn: working memory re-seeds, PersonalContextService builds their context,
    behaviour learning attributes to them
```

## 5. Added 13 July, from the full-codebase architecture review

Three items folded into this milestone's scope rather than treated as separate fixes (full detail in `ENGINEERING_BACKLOG.md`):

1. **Wire the `SEARCHING` identity state.** `IdentityStateMachine.evaluate()` currently can never produce `SEARCHING`/`DETECTED`, even though both are already defined in `IdentityTypes` and referenced elsewhere. v0.16 needs exactly this state (face detected, quality check passed, recognition call in flight) — build it into the state machine as part of this milestone.
2. **`PersonRegistry.protected` is the canonical "is this person protected" source.** Three independent checks exist in the codebase today; face recognition should read/write against `PersonRegistry` only and must not introduce a fourth.
3. **Camera-agnostic by convention, not by new abstraction.** Christian has raised a future multi-camera monitoring phase (WiFi/Bluetooth pan-tilt cameras around the house, added to the MVCH as Phase 9, v0.18.x, positioned after this milestone and Protected User Alerting, before Robot Control). No new camera abstraction needs building now, but new face-recognition code should take a frame as input rather than reaching into `CameraService`'s singleton state directly, so it isn't harder to retrofit onto multiple camera sources later.
