## 2. The single most important thing: you are NOT building alerting from scratch — but it's split across three unconnected systems

Unlike Face Recognition (which had one clean, deliberately-unfinished slot to fill), Protected User Alerting has **three separate subsystems that already do real work, that don't talk to each other yet.** Your first real job is deciding how they connect, not building a fourth one.

**A. Risk scoring already exists — in the Behaviour layer, not a dedicated "risk assessment" service.**
- **`services/behaviour/BehaviourRiskScoring.js`** — `score({ observations, protectedUser, inactiveDurationSeconds })` already assigns points for exactly the scenarios that matter here: `BODY_POSITIONS.FLOOR` (+35), `MOVEMENT_STATES.FALL_DETECTED` (+45), `BODY_POSITIONS.LYING` (+25), unusual head direction (+25), and takes a `protectedUser` flag as input. **This is most of "v0.17.1 Risk Assessment Engine" already built** — the gap is that nothing currently feeds it a real, live, person-scoped `protectedUser` flag from `PersonRegistry`/Face Recognition, and its output doesn't yet reach the notification layer in a first-class way. Read this file fully before assuming you need to build risk scoring from zero.
- **`services/behaviour/BehaviourProfileMatcher.js`** — user-defined "Behaviour Library" labels exist but never feed into the numeric score (a disclosed, unresolved gap in `ENGINEERING_BACKLOG.md`). Decide whether v0.17.1 should finally reconcile these two.

**B. There are TWO parallel, non-interoperable notification pipelines. Only one is wired to the UI.**
- **Pipeline 1:** `NotificationPolicy.evaluate(decision, userContext)` → `NotificationQueue`. Uses `NOTIFICATION_TYPES` (`PROTECTED_USER_ATTENTION` already exists as a type!) and `NOTIFICATION_PRIORITIES` (LOW/NORMAL/HIGH/URGENT), reads `UserPermissions.canReceiveProtectedUserAlerts(role)`. **Not wired to any UI.**
- **Pipeline 2:** `NotificationEngine.js` (`createFromDecision`/`evaluateDecision`) → `NotificationProfiles`/`NotificationTargets`. Uses a different priority scale (`NOTIFICATION_PRIORITY`: CRITICAL/ASSIST/ATTENTION/OBSERVATION, score-thresholded 85/65/40/20) and a different targets model (`NOTIFICATION_TARGET`: `ROBOT_VOICE`, `ANDROID_NOTIFICATION` (status: `LOCAL_ONLY`, i.e. real-ish), `GALAXY_WATCH`/`TRUSTED_CONTACT`/`BASE_STATION`/`CLOUD_SERVICE` (status: `PLANNED`, i.e. stubs). **This is the one wired to UI/diagnostics.**
- These two pipelines duplicate the same concept (decision → priority → who gets told) with incompatible vocabularies and were flagged in `ENGINEERING_BACKLOG.md` with the explicit recommendation: **"consolidate when v0.17 forces a decision on real delivery channels anyway — don't do it twice."** That moment is now. Scoping this milestone means picking one (or a genuine merge) before building escalation on top of either.

**C. The user/role/permission model exists and has real protected-user semantics — but has zero live callers.**
- **`services/users/UserRoles.js`** — `PROTECTED_USER` role, priority-ranked below `TRUSTED_USER`/`OWNER`/`ADMINISTRATOR`.
- **`services/users/UserPermissions.js`** — `RECEIVE_PROTECTED_USER_ALERTS` permission already exists, granted to `OWNER`/`ADMINISTRATOR` only (not `TRUSTED_USER`) — i.e. the permission model already encodes "only certain people should hear about Finley's alerts," you just need to decide if that's still the right rule.
- **`services/users/ProtectedUserService.js`** — `createProtectedUserContext(userProfile)` already returns `{ protected: true, observationPriority: 'elevated_non_medical_observation', notificationPriority: 'high', medicalDiagnosis: false }` — this is a ready-made bridge between "is this person protected" and "how urgently should MARS treat what it's seeing," and it already carries the `medicalDiagnosis: false` safety flag baked in.
- **None of `UserManager.registerFromIdentity()`/`resolveUserContext()` are called anywhere in the live app.** `PersonRegistry` (from the Identity/Face Recognition work) is what actually drives behaviour today — it has its own, separate notion of `PROTECTED_USER` (used directly in v0.16.13's priority-selection logic: `perFaceResults.find(entry => entry.identity.protected)`). **You likely have two different "is this person protected" sources of truth** (`PersonRegistry` profile flags vs. `services/users` roles) that were never reconciled. This needs a decision, not a guess.

**D. The actual trigger signal for "can't see them, are they OK" now exists, freshly built last session.**
- `IdentityLockService`/`identityHeld`/`identityLocked` (v0.16.11–v0.16.14) is the real answer to "MARS lost visual contact with a locked-on protected user." Today it only feeds the Identity/Vision UI badges — it does **not** yet feed the Behaviour/Risk/Notification chain at all. Wiring `identityHeld` (plus how long it's been held, and combining it with `BehaviourRiskScoring`'s floor/fall/lying signals) into a real risk/alert decision is likely the single most natural, highest-value connective piece of v0.17.1 — this is quite literally the "Finley has a seizure and is on the floor" scenario Christian originally described when asking for Identity Lock, now needing its second half: turning "still tracking him" into "someone should be told."

## 3. Decisions to put to Christian at scoping (risk-tiered, don't decide these unilaterally)

1. **Consolidate the two notification pipelines, or keep both and pick one as canonical for new work?** Recommendation to offer: adopt `NotificationEngine`/`NotificationProfiles`/`NotificationTargets` (Pipeline 2) as canonical since it's the one already wired to UI/diagnostics, formally deprecate `NotificationPolicy`/`NotificationQueue` (Pipeline 1) in docs, but keep `NOTIFICATION_TYPES.PROTECTED_USER_ATTENTION`'s naming/intent — it's a good concept, just currently on the wrong pipeline.
2. **Which delivery channel is v0.17's real target, if any?** `NOTIFICATION_TARGET.ANDROID_NOTIFICATION` is the only non-`PLANNED` status today (`LOCAL_ONLY`). Is v0.17 Foundation allowed to ship a real local browser/device notification (e.g. the Notifications API, or an in-app banner) as its first genuinely-delivered alert, with `TRUSTED_CONTACT`/`GALAXY_WATCH`/SMS/push remaining honest stubs? Or is a fully-simulated escalation state machine (no real delivery yet) the right Foundation scope, matching how every other phase's Foundation milestone has worked (build the real pipeline, keep the actual "send" simulated/local until a later milestone)? Likely recommendation: the latter — consistent with the project's established pattern (Voice Foundation, Behaviour Foundation, Face Recognition Foundation all did this).
3. **Reconcile `PersonRegistry`'s protected flag with `services/users`' `PROTECTED_USER` role/permissions, or leave `services/users` formally un-integrated?** This was flagged as an open question in `ENGINEERING_BACKLOG.md` before this session even started. v0.17 is the first milestone where it actually matters (permissions govern who receives protected-user alerts). Recommendation to offer: keep `PersonRegistry` as the single source of truth for "who is protected" (it's already live and wired into Identity Lock's priority selection), and have `UserPermissions.canReceiveProtectedUserAlerts()` be evaluated against whoever's *receiving* the alert (the owner/trusted user), not the protected person themselves — these are two different roles in the same flow and shouldn't be conflated.
4. **Does the Risk Assessment Engine (v0.17.1) extend `BehaviourRiskScoring` in place, or wrap it in a new person-scoped service?** Recommendation to offer: extend in place if possible (it's already close, and its inputs — observations, protectedUser, inactiveDuration — map naturally onto Identity Lock's `identityHeld`-duration signal) rather than building a parallel scorer.

## 4. Safety & privacy rules specific to alerting (carry these in, they compound the existing ones)

- **`medicalDiagnosis: false` on every risk/alert decision, no exceptions.** `ProtectedUserService.createProtectedUserContext()` already bakes this in — don't build a path that drops it.
- **Frame everything as "this looks different from normal, a human should check" — never "this is a seizure" / "this is a fall" as a clinical assertion.** The wording in `BehaviourRiskScoring`'s existing `reasons` array ("Person appears to be on the floor," "Movement observation suggests...") is the right register — hedged, observational, non-diagnostic. Keep new copy consistent with that tone.
- **False alerts have a real cost (alert fatigue for the humans who'd act on them); missed alerts have a real cost (the whole reason this phase exists).** Whatever escalation thresholds/timers you propose, name this trade-off explicitly to Christian rather than picking numbers silently.
- **Who receives a protected-user alert is itself a safety-relevant access-control decision** — this is why `UserPermissions.RECEIVE_PROTECTED_USER_ALERTS` deliberately excludes `TRUSTED_USER` (only `OWNER`/`ADMINISTRATOR` today). Don't loosen this without Christian's explicit sign-off.
- **On-prem/privacy posture carries forward:** if any alert content is ever templated through an LLM (e.g. "compose a message to send"), it must follow the same on-prem-only rule as `PersonalContextService` — no protected-user observation data to the Cloud tier.

## 5. The end-to-end flow to build (target architecture, sketch — refine during scoping)

```
VisionPipeline (per-frame, per-face; already emits identityRoster + identityHeld/identityLocked)
  → BehaviourRiskScoring.score({ observations, protectedUser, inactiveDurationSeconds })
      [EXTEND: feed it identityHeld + how-long-held from IdentityLockService,
       and protectedUser sourced from PersonRegistry, not services/users]
  → NEW: a person-scoped Risk Assessment step that turns a score + duration
    into a decision-worthy "concern level" over time (a single bad frame
    shouldn't alert; a sustained pattern should) — this is the actual
    "Engine" part of v0.17.1, likely a small state machine similar in
    spirit to IdentityLockService's leaky-bucket hysteresis
  → DecisionEngine / DecisionIntelligenceService (existing, decide whether
    to route through it as-is or extend)
  → NotificationEngine.evaluateDecision() [canonical pipeline, pending
    Christian's decision in §3.1]
  → NEW: Alert Routing & Escalation (v0.17.2) — an actual state machine:
    first attempt → no ack within N → escalate to next contact/channel →
    ... — today NotificationQueue/NotificationHistory exist but there is
    no escalation-over-time logic anywhere
  → delivery: real for ANDROID_NOTIFICATION/local (per §3.2 decision),
    simulated/stub for everything else (TRUSTED_CONTACT, GALAXY_WATCH, etc.)
  → v0.17.3 Protected User Monitoring Dashboard: a UI surface (new tab or
    section) showing current risk level, active/recent alerts, and
    escalation state per protected user — this is the first UI this phase
    needs beyond what already exists
```

- **Run npm from `mars-standalone/`**, never the repo root.
- **Two "is this person protected" sources of truth already exist** (`PersonRegistry` vs. `services/users`) — see §2C/§3.3. Don't silently pick one without flagging it; it's a real architectural fork, not a style preference.
- **Two notification pipelines already exist** (§2B) — same caution.
