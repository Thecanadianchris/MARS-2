## 2. The single most important thing: you are NOT building identity from scratch

MARS already has a full **identity framework** (v0.13.0–v0.13.2) that was deliberately built to *receive* a future recognizer. Read these before scoping:

- **`services/identity/IdentityEngine.js`** — orchestrates identity. `evaluate(perceptionResult, options)` runs the state machine and resolves a matched profile. It literally reports `recognitionProvider: 'not_implemented_in_v0.13.1'`, `faceRecognitionActive: false`, `preparedForFutureRecognition: true`. There is already `evaluateRecognitionCandidate(candidate, options)` — **this is the slot your recognizer plugs into.**
- **`services/identity/RecognitionCandidate.js`** — the provider-neutral candidate shape (`candidateProfiles`, `trackingId`, `faceVisible`, confidence). Your recognizer's job is to produce one of these.
- **`services/identity/IdentityStateMachine.js` + `IdentityTypes.js`** — states already exist: `NO_PERSON → DETECTED → TRACKING → SEARCHING → UNKNOWN / PENDING_PROFILE / GUEST / KNOWN / TRUSTED / PROTECTED / BLOCKED`, plus events (`PROFILE_MATCHED`, `PROFILE_PENDING`, `PROFILE_CONFIRMED`).
- **`services/identity/PersonRegistry.js`** — people in an unbounded Map (`christian` OWNER, `ann` TRUSTED_USER, `finley` PROTECTED_USER) with a **`createPendingProfile` → `confirmPendingProfile`** flow (trusted-user-gated via `ProfileAuthorisationService`). New/unknown faces become *pending* profiles a trusted user confirms — that flow already exists; don't rebuild it.
- **`services/identity/FaceQualityEngine.js`, `RecognitionConfidence.js`, `IdentityTrackingService.js`** — scaffolding for face-quality scoring, confidence, and cross-frame tracking.
- **`services/vision/FaceFoundationEngine.js`** — note: this is face *presence + head orientation* from MediaPipe **pose** landmarks. It is explicitly **NOT** recognition (it answers "is a head visible / which way is it facing", not "whose face"). It gives you `faceDetected`.
- **Live vision exists:** `services/vision/` (VisionPipeline, VisionService, PoseDetectionService, CameraService, FrameCaptureService) runs a real camera + MediaPipe. `@mediapipe/tasks-vision` is already a dependency (it also offers `FaceDetector` and `FaceLandmarker`, which are **not** used yet — only pose is).
- **UI:** `components/identity/IdentityPanel.jsx` + `hooks/useIdentityFoundation.js` — identity is currently **simulation-driven** in the panel (like behaviour), with scenario inputs. There's an **ID** tab already.
- **Memory wiring point (the payoff):** `MemoryIntelligenceService.setActivePerson(personId)` already exists and is unit-tested. When you call it, `getActivePersonId()` returns that person, and the engine seeds working memory + `PersonalContextService` builds that person's context on the next turn. Confirm this by reading `services/memory/MemoryIntelligenceService.js` and `WorkingMemorySmokeTest`/`PersonalContextSmokeTest`.

So v0.16 = **fill the RecognitionCandidate slot with a real (or honest-stub) recognizer, add face registration, and wire a confirmed KNOWN identity → `setActivePerson`.**

## 3. THE decision to put to Christian at scoping: how does recognition actually work in a browser?

This is the crux and it's genuinely a fork — present it as risk-tiered options and let Christian choose before building:

- **Option A — Landmark-geometry signature (deterministic, no model download).** Use MediaPipe `FaceLandmarker` and derive a "face signature" from landmark ratios/distances; match by nearest-signature within a threshold. Pros: no extra ML dependency, fully in the existing MediaPipe stack, deterministic/testable. Cons: weak, pose/lighting-sensitive, not real biometric-grade recognition — fine for a Foundation demo, not robust.
- **Option B — Real face-embedding model.** Add a face-recognition model (e.g. a TFLite/ONNX face-embedding model, or `face-api.js`). Pros: robust embeddings, real recognition. Cons: new dependency + model download (bundle/size), more moving parts, more to test; heavier for a Foundation.
- **Option C — Honest-stub Foundation (matches every prior "Foundation").** Build the full pipeline — a pluggable `FaceRecognitionService` interface that emits `RecognitionCandidate`s, the registration flow, the `IdentityEngine` wiring, and the `setActivePerson` payoff — but keep the actual matcher a simple/simulated recognizer (or Option A's geometry) behind the interface, deferring a heavy real model to v0.16.1/0.16.2 or the Android build (v0.19.x). Pros: consistent with how Voice/Identity/Behaviour Foundations were built, lowest risk, still delivers the end-to-end wiring and the memory payoff. Cons: recognition isn't robust yet.

**Likely recommendation (yours to argue, Christian's to decide): Option C** — establish the pipeline + registration + `setActivePerson` wiring end-to-end with a pluggable recognizer, so the architecture and the memory payoff are real and tested, and the heavy model is a later, isolated swap. But surface A and B honestly.

## 4. Safety & privacy rules specific to face recognition (carry these in)

Face recognition of vulnerable, monitored people is sensitive. Establish up front:

- **Biometric data stays on-device.** Any face signature/descriptor/embedding is stored locally only (same on-prem posture as personal context). Never send face data to any cloud service.
- **A wrong recognition is a real harm vector:** mis-identifying person A as person B would load B's memory + personal context into the AI and could mis-route a future safety alert. So **gate `setActivePerson` behind a high confidence threshold**, and never silently switch to a *protected user's* context on a weak match.
- **Unknown faces are never auto-enrolled.** New faces go through the existing `createPendingProfile → confirmProfile` trusted-user gate. No silent registration.
- **`medicalDiagnosis: false`** and all existing safety flags carry forward. Face recognition identifies *who*, never anything clinical.
- Follow the same regression discipline as Phase 6: additive wiring, explicit guard tests, don't disturb the memory writer paths or which turns escalate.

## 5. The end-to-end flow to build (target architecture)

```
camera frame (CameraService / FrameCaptureService)
  → FaceRecognitionService (NEW) produces a RecognitionCandidate
      - known match ≥ threshold  → candidateProfiles: [{ profileId, confidence }]
      - unknown / low confidence  → no match → PENDING_PROFILE path (trusted-user confirm)
  → IdentityEngine.evaluateRecognitionCandidate(candidate)  [already exists]
      → resolves KNOWN / UNKNOWN / PENDING state + matched profile
  → on a confirmed KNOWN identity above threshold:
      MemoryIntelligenceService.setActivePerson(profile.id)   ← the payoff
  → next conversation turn: working memory re-seeds for that person,
    PersonalContextService builds THEIR on-prem context, behaviour learning attributes to THEM
  → Face registration UI (v0.16.1): enrol a known person's face signature keyed by personId
  → Diagnostics in the ID tab (v0.16.3): live recognition state, confidence, active person
```
